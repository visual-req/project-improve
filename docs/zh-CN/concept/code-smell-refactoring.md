# 代码坏味道与重构

“代码坏味道（Code Smell）”指的是代码中那些不一定立刻造成 bug，但会持续增加理解成本、修改成本与缺陷概率的信号。  
“重构（Refactoring）”是以不改变外部可观察行为为前提，持续改进代码结构的过程。

## 为什么坏味道会变成项目阻碍点

- 评审变慢：代码难读 → reviewer 不敢确认风险 → review latency 上升
- 修改变慢：影响面不清晰 → 改一处坏多处 → lead time/cycle time 上升
- 质量变差：缺陷更易引入 → 缺陷率、重开率、缺陷逃逸率上升
- 自动化失效：构建慢/测试难写 → CI 失败率上升、覆盖率长期不动

## 常见代码坏味道（按“阻碍类型”归类）

### 1) 可理解性坏味道（评审阻碍）

- 超长函数/超长类（Long Method / God Class）
- 命名不清晰、语义漂移（变量/函数名与行为不一致）
- 过多分支与嵌套（Cyclomatic Complexity 高）
- 跨层混杂（业务逻辑与 IO/框架细节混在一起）
- 注释解释“为什么这样写”：通常意味着代码意图本身不清晰（可以用更好的命名/拆分替代）
- 布尔参数/多参数函数：调用点难理解，易引入误用

### 2) 可修改性坏味道（交付阻碍）

- 重复代码（Duplicated Code）：改动需要多处同步，容易漏
- 散弹式修改（Shotgun Surgery）：一个需求需要改很多文件/模块
- 霰弹枪继承/过度抽象：抽象层多但不稳定，改动成本更高
- 原始类型偏执（Primitive Obsession）：缺少领域对象与约束，错误更隐蔽
- 特性嫉妒（Feature Envy）：逻辑频繁访问别的对象内部数据，边界不清晰
- 数据泥团（Data Clumps）：一组参数/字段总是一起出现但没有被抽成对象
- 临时字段/死代码：历史遗留导致逻辑分叉，增加认知负担

### 3) 可测试性坏味道（质量左移阻碍）

- 强耦合外部系统（数据库/HTTP/时钟）且不可替换：单元测试难写
- 副作用到处散落：难以隔离、难以断言
- 缺少边界与接口：无法对关键用例做稳定测试
- 非确定性（依赖时间/随机数/并发时序）：测试不稳定，CI 失败率上升
- 大量静态/全局状态：测试互相污染，难并行、难定位

## 为什么 Sonar 扫描能发现这些问题

Sonar 之所以能发现“坏味道”，本质是它把大量可量化的静态信号（代码结构、控制流、重复片段、复杂度、依赖关系、常见错误模式）映射为规则，并在 PR/CI 中持续执行。

常见映射关系：

- 复杂度过高（坏味道：过多分支与嵌套/超长函数）  
  Sonar 通常会给出 Cognitive Complexity / Cyclomatic Complexity 超阈值提示

- 重复代码（坏味道：Duplicated Code）  
  Sonar 会做 token/片段级相似度检测，给出重复比例与位置

- 资源未释放/异常处理缺陷（坏味道：副作用不可控）  
  Sonar 会通过模式匹配与数据流分析，提示潜在泄露与异常路径问题

- 依赖与边界问题（坏味道：跨层混杂/不可测性）  
  Sonar 的一些规则会提示层级违规、包依赖循环、过度耦合等信号（取决于语言与启用规则集）

需要注意：Sonar 发现的是“风险信号”，不是最终结论。最佳用法是：

- 把 blocker/critical 作为门禁（避免明显问题进入主干）
- 把 code smells 作为重构线索（结合业务上下文与指标，选最有杠杆的点）

## 重构的基本原则（让重构可控、可验收）

- 小步提交：每次变更尽量只做一个结构性调整，方便回滚与评审
- 先写保护网：优先补齐关键用例测试，再做结构重排
- 先把“行为固定”再优化结构：避免“重构 + 改需求”混在一次 PR
- 把重构接到度量：用变更规模、评审等待、缺陷回流等信号验证改动价值

## 常见重构手法（与坏味道一一对应）

- 提取函数/提取类：降低单点复杂度，提高可读性
- 引入领域对象：把“原始类型 + 约束”封装起来，减少错误空间
- 分离副作用：把 IO/框架调用与纯业务逻辑分开，提高可测试性
- 依赖反转：用接口隔离外部系统，使测试可注入替身
- 拆分大 PR：把大变更分成可独立验证的小步骤

## 什么时候把坏味道写入行动项

当坏味道已经影响交付与质量，并且具备“可验证目标”时，就应该进入行动项排期。例如：

- “review latency p75 偏高，主要集中在某模块的超大 PR 与复杂函数上”  
  行动：限制 PR 规模 + 提取复杂函数 + 增加关键测试；验收：两个窗口内 review latency p75 下降

- “缺陷回流集中在边界条件，且模块几乎不可测试”  
  行动：引入可测试接口 + 补齐边界用例测试；验收：重开率下降、缺陷逃逸率下降

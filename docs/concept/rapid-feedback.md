# 快速反馈（Rapid Feedback）

快速反馈的目标是缩短“做出一个变更 → 得到可信反馈 → 调整方向”的周期，让问题在影响扩大之前被发现并解决。

## 为什么快速反馈是持续改进的核心

- 反馈越晚，修复越贵：上下文丢失、影响扩大、返工成本高
- 反馈越慢，团队越倾向于大批量提交：导致评审、测试、发布扎堆，风险更高
- 没有反馈就没有学习：持续改进会退化成口号与模板

## 常见的反馈回路（从快到慢）

1. 编辑器/静态检查（秒级）：lint、类型检查、格式化
2. 单元测试（分钟级）：核心规则与边界条件
3. PR 评审（小时级）：变更影响面、风险点、回滚策略
4. CI 集成（分钟到小时）：构建稳定性、扫描、集成测试
5. 预发/灰度（小时到天）：真实环境与真实流量下的验证
6. 线上监控（分钟到天）：错误率、延迟、业务指标、告警与值班

关键原则：反馈越靠前，越适合拦截“低成本修复的问题”；反馈越靠后，越适合验证“系统级效果与副作用”。

## 如何把快速反馈落到机制（可执行）

- 小批量交付：限制 PR 规模与变更批量，让反馈更快更准
- 质量门禁前移：扫描/测试在合并前强制执行，失败不能随意跳过
- 让阻碍可见：燃尽偏离、看板堆积、评审等待变长时立即处理
- 把反馈接到行动项：每个行动项都要写清验收方法与对比窗口

## 与 ORID 的关系

快速反馈为 ORID 提供高质量的 O 段事实（可复核数据）。当团队能快速得到反馈，R 段的摩擦会下降，I 段假设更容易验证，D 段行动也更容易闭环。

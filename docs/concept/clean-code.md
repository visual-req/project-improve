# 整洁代码（Clean Code）

整洁代码不是“风格好看”，而是让代码在长期演进中保持可理解、可修改、可测试，从而减少交付阻碍与质量回流。

## 整洁代码的目标

- 让阅读成本低：评审与接手更快（降低 review latency）
- 让修改成本低：改动影响面清晰（降低 lead/cycle time）
- 让缺陷更难产生：约束与测试更完善（降低缺陷率、重开率、缺陷逃逸率）

## 常见原则（可执行版本）

### 1) 命名清晰

- 名字表达“意图”，避免缩写与含糊词（data/info/tmp）
- 同一概念只用一种词（避免同义混用导致语义漂移）

### 2) 函数短小且单一职责

- 一个函数最好只回答一个问题
- 分支与嵌套过深通常意味着需要拆分或引入策略

### 3) 依赖与副作用可控

- 把纯业务逻辑与 IO/框架调用分离
- 外部依赖（DB/HTTP/时钟/随机数）通过注入隔离，便于测试

### 4) 错误处理可预测

- 统一错误语义与边界（哪些错误可以重试、哪些需要回滚）
- 日志、指标与追踪对关键路径一致（便于定位线上问题）

### 5) 测试是设计的一部分

- 单元测试覆盖关键业务规则与边界条件
- 集成测试覆盖关键链路（依赖真实外部系统时，用稳定的测试环境与数据基座）

## 把“整洁”落到团队机制（避免口号）

可用以下方式把整洁代码变成系统能力：

- PR Checklist：变更规模、测试、扫描结果、风险提示、回滚策略
- DoD：必须满足的最低质量门槛（例如无新增 blocker、关键用例覆盖）
- 自动化门禁：lint/format/类型检查/扫描/测试在 CI 中强制执行

## 常见误区

- 只做格式化与命名统一，不处理复杂度与边界：仍然难改、难测
- 把“整洁”当作一次性运动：没有机制与门禁，质量会自然回滑
- 把整洁代码当成个体要求：没有工作流与工具支持，成本会转嫁给个人

# ORID

![ORID推进过程](../assets/orid-process.svg)

ORID 用于把“数据事实”转化为“可执行改进”，并且强制把不同类型的讨论分层，避免把事实、情绪与解释混在一起：

- O（Objective）：客观事实（指标、趋势、异常样本）
- R（Reflective）：团队感受/摩擦点（不归因个人）
- I（Interpretive）：原因假设与解释（证据 + 反证 + 数据缺口）
- D（Decisional）：决策与行动方向（约束、优先级、验证方式）

## 为什么要拆成四个步骤

1. 防止“事实被情绪污染”：如果在同一轮讨论里边摆事实边评价，很容易把结论变成“我觉得/你不行”。
2. 防止“解释抢跑”：在事实尚未稳定前就下结论，会把讨论锁死在错误方向上，后续只是在找证据“证明自己是对的”。
3. 让反证有位置：I 段要求明确反证与数据缺口，逼迫团队承认不确定性与可验证路径。
4. 让行动可验证：D 段输出的是“可验收的决策方向”，它必须能映射到行动项与下一窗口对比。

## 先确保客观数据：收集与准确性

根因分析与行动排期的质量上限，来自 O 段事实的质量。建议在进入 ORID 前先完成两件事：

1. 明确数据窗口与边界
   - 时间窗：滚动 30 天 / 一个迭代 / 多个迭代（保持一致，便于对比）
   - 范围：项目/团队/仓库/看板（避免“拿 A 项目的数据解释 B 项目的问题”）

2. 做数据准确性与完整性校验（data integrity）
   - 字段缺失：关键时间戳（created/started/done）、状态历史、迭代字段、缺陷严重度、线上标识等是否齐全
   - 口径一致：状态集合（wip/done）、过滤规则（issue type/labels）、跨系统映射（Jira 字段 vs Git PR 字段）是否对齐
   - 异常值：时间戳逆序、跨时区导致的日期偏移、重复/缺失记录、极端长尾样本（需抽样核对）

如果数据缺口会影响某条结论，必须在 I 段显式标注“当前无法确认/需要补采什么数据/如何补采”。

## 四段输出怎么写（细化）

### O · Objective（事实）

输入：指标、趋势、阈值判定、异常样本 Top N（如 aging wip、重开条目、review 延迟条目、线上缺陷）。

输出原则：

- 每条事实都要可复核（来源、窗口、口径明确）
- 以“观察到”开头，避免解释与归因

### R · Reflective（感受/摩擦）

输入：O 段事实。

输出原则：

- 把事实翻译成团队摩擦点（等待、返工、不确定、协调成本），不要指向个人评价
- 用“我们感到/我们经常遇到”表达，避免“你/他们”

### I · Interpretive（解释/假设）

输入：O 段事实 + data_integrity（数据缺口）。

输出原则：

- 每条假设必须同时写：支持证据 + 反证（什么情况会推翻）+ 需要补采的数据
- 假设优先落在机制层：入口标准、WIP、接口契约、协作节奏、自动化缺口、系统约束

### D · Decisional（决策方向）

输入：I 段假设（含可验证路径）。

输出原则：

- 输出“方向/规则/约束/优先级/验证方式”，而不是直接写任务清单
- 每条方向至少绑定 1 个验证指标与下一窗口检查方式

## 根因分析过程（从 ORID 走向原因树）

本系统的根因分析强调“可证据支撑、可反证、可落地验证”，建议按以下顺序梳理：

1. 从指标与样本出发：只从 O 段的事实进入分析（数值、趋势、异常 Top N）
2. 形成问题表述：将偏差点改写为中性可讨论的问题（避免指责个人）
3. 生成原因假设：围绕流程、协作、系统约束、依赖关系提出假设
4. 证据与反证：为每个假设列出支持证据，并明确什么数据会推翻它
5. 补齐数据缺口：将 data_integrity 中的缺口映射到“为什么无法确认/如何补采”
6. 选择优先根因：优先选择影响面大、可控、能在下一窗口验证的根因

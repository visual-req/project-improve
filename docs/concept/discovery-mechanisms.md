# 沟通协作与文档问题的发现机制

很多项目问题不是“技术不会做”，而是协作接口不清、信息不同步、文档失真导致的返工与等待。要把这类问题尽早发现并扼杀在早期，需要建立明确的发现机制与触发信号。

## 沟通与协作问题：如何尽早发现

### 1) 阻碍显性化（Daily Scrum / 看板）

把阻碍从“抱怨”变成“可跟踪事项”：

- 每个阻碍必须写清：阻碍点是什么、影响谁、需要谁、预计多久解除
- 阻碍必须有负责人（owner）与时间盒（timebox）
- 阻碍一旦跨日，默认进入当天最高优先级处理

可观察信号（触发讨论/改进）：

- 阻碍数量持续上升或长期不下降
- 某泳道长期堆积（Review/Testing/Release）
- 交接等待时间显著变长（review latency、testing wait）

### 2) 需求澄清往返次数（需求接口问题）

当出现这些现象，通常说明“协作接口/上下文”缺失：

- 同一个需求反复澄清、频繁改口径
- 验收失败与重开集中出现
- 需求与实现之间存在“默认理解”，没有明确契约

最小改进动作：

- 引入 1 页验收清单（关键路径/边界/回滚/监控）
- 对高风险需求增加一次 15–30 分钟的对齐（包括 QA/运维/依赖方）

### 3) PR 评审等待与反复返工（工程协作接口问题）

协作问题常见地“体现在代码评审里”：

- review latency 上升：评审排队、上下文不足、变更过大
- PR 来回多轮：风险点不清、关注点不一致、门禁不明确

最小改进动作：

- 限制单次 PR 规模 + 引入设计摘要模板
- 明确评审关注点与质量门禁（扫描/测试必须通过）

## 文档问题：如何尽早发现

文档问题常见表现不是“没有文档”，而是：

- 文档过期：行为已经变了，文档还停留在旧版本
- 文档不可执行：只有描述没有示例、没有边界、没有失败路径
- 文档不可信：无法从文档复现流程或验证结论

### 1) 文档与代码绑定（让文档可验证）

把文档变成可验证的交付物：

- 接口契约与示例：请求/响应示例、错误语义、兼容策略
- Runbook：关键操作与回滚步骤可复现
- 变更记录：重大变更必须附“影响面与迁移方式”

触发信号：

- Onboarding 需要口头传授才能完成
- 线上问题排查依赖“问人”
- 同类问题重复出现但没有沉淀

### 2) 文档评审机制（像评审代码一样评审文档）

最小机制：

- 文档变更走 PR，与代码一起评审
- 文档必须包含“目标、前置、步骤、验证、失败处理”
- 文档必须标注版本与适用范围（项目/模块/时间窗）

## 把发现机制接到 ORID

建议做法：

- 把“阻碍点、澄清往返、评审等待、文档失真”写进 O 段事实（可引用、可复核）
- 在 I 段提出机制层假设（接口契约、入口标准、WIP、责任边界、工具门禁）
- 在 D 段形成行动项与验收方式（下一窗口对比）

# I（补充）· 根因思维导图（原因树 + 权重）

目标：不要机械追问 why。用“思维导图/原因树”的方式把现象的各种可能原因展开到叶子节点，并为叶子原因分配权重，形成可视化根因图。

## 输入

- O 段事实（指标/趋势/异常样本）
- R 段摩擦点
- I 段原因假设（可作为一级分支的候选）
- data_integrity（用于标注哪些原因缺乏数据支撑）

## 选择现象（Phenomenon）

选择 1–3 个最关键“现象”作为根节点（建议来自红色指标或高风险样本），例如：

- 交付变慢（Lead/Cycle 上升，Aging WIP 增多）
- 质量外溢（缺陷逃逸率增多，重开率上升）
- 协作反馈慢（Review Latency 上升，PR 长时间未合并）

## 原因树展开方法（建议结构）

对每个现象构建一棵原因树：

1. 根节点：现象（带证据引用）
2. 一级分支：按维度展开（建议至少覆盖下面 6 大类，避免把复杂问题简化成单线因果）
   - 能力与知识（Capability）
     - 业务理解：评审/开发是否理解关键业务规则、边界与风险点
     - 技术能力：关键模块/语言/框架是否存在知识盲区
     - 复杂度应对：是否具备拆分、抽象、降耦合的能力与约束
     - 经验模式：是否存在反复踩坑的“已知失败模式”（例如缓存一致性、并发竞态、状态机遗漏）
   - 环境与约束（Environment）
     - 人力与负载：多项目并行、值班/线上事件、临时插单对节奏的扰动
     - 依赖与外部因素：上游接口不稳定、依赖团队交付延迟、审批/合规流程
     - 工具与基础设施：构建/测试环境不稳定、权限/网络限制、数据源不可用
   - 质量标准与定义（Quality Standard）
     - DoD/验收标准：完成的定义是否清晰、是否可检验、是否被执行
     - 评审标准：评审关注点是否明确（正确性/风险/可维护性/可测试性/安全）
     - 缺陷口径：Bug/逃逸缺陷/重开如何定义，是否跨系统一致
     - 质量门禁：代码扫描、测试覆盖率、发布前检查是否形成门禁
   - 流程与协作（Process）
     - WIP 与排队：是否存在过载导致的排队、上下游阻塞、跨团队等待
     - 评审流程：评审 SLA、轮值机制、响应机制、评审批量与节奏
     - 需求流：需求澄清/变更控制/拆分粒度/依赖识别是否到位
     - 反馈回路：测试/线上反馈是否能快速回流到需求与实现
   - 设计与实现（Design / Implementation）
     - 复杂度：模块耦合度高、代码可读性差、变更规模过大导致理解成本高
     - 架构边界：职责边界不清、接口契约不稳定、缺少可替换/可回滚策略
     - 可测试性：缺少隔离点、难以编写自动化测试、环境依赖强
   - 工具与自动化（Tooling / Automation）
     - CI/CD：流水线稳定性、反馈时延、失败定位成本
     - 测试自动化：覆盖关键路径、回归效率、用例维护成本
     - 可观测性：日志/指标/告警是否支撑快速定位与复盘
3. 二级及以下：每个分支继续展开为“原因的原因”，直到叶子节点满足：
   - 可行动（能对应一个具体改动/机制/规则）
   - 可验证（能绑定指标或过程检查点）
   - 可归档（能在 report.json 中表达）

## 展开时的强制检查（避免“流于表面”）

对每个叶子原因补齐下面信息（缺一项则标记低置信度）：

1. 证据：对应哪些指标/样本/现象（引用 O 段事实）
2. 反证：什么情况发生时，这个原因就不成立（用于避免单向归因）
3. 验证方式：下一窗口用什么数据/抽样/审计来验证（可执行）
4. 行动映射：能落到哪条行动项字段（owner、due_date、acceptance_method）
5. 边界：该原因解释的是“普遍现象”还是“少数异常样本”

## 权重（Weight）分配

对每棵原因树的叶子节点分配权重，表示其对现象的贡献度（建议 0–1 之间，总和 = 1）：

- 权重依据：证据强度（指标/样本）、影响范围、出现频率、可解释度
- 若数据不足：仍可给出权重，但必须标注 `confidence: low` 或写入 evidence 中的缺口说明

内部节点权重 = 子节点权重之和（用于前端展示聚合权重）。

## 输出 JSON（根因图）

输出一个 `root_cause_map` 对象，并建议落盘：

- `work/outputs/<project_id>/project-metrics-orid/root-cause-map.json`

JSON schema（建议）：

```json
{
  "version": 1,
  "project_id": "proj-123",
  "generated_at": "2026-06-04T12:00:00Z",
  "phenomena": [
    {
      "id": "phen-1",
      "title": "交付变慢",
      "evidence": ["Lead Time p50 由 6.2d 上升到 9.1d", "Aging WIP > 14d 的条目 12 个"],
      "root": {
        "id": "n-root",
        "title": "交付变慢",
        "children": [
          {
            "id": "n-req",
            "title": "需求/入口",
            "children": [
              { "id": "n-req-1", "title": "需求拆分粒度过大", "weight": 0.18, "confidence": "medium", "evidence": ["Story 平均 points 上升"] }
            ]
          }
        ]
      }
    }
  ]
}
```

节点字段约定：

- `title`：必填
- `children`：数组（可空或缺省）
- `weight`：仅叶子节点必填（0–1）；内部节点由前端/后处理聚合
- `confidence`：low/medium/high（可选）
- `evidence`：数组（可选）
- `anti_evidence`：数组（可选，用于记录反证或数据缺口）
- `verification`：对象（可选，例如 { "method": "...", "owner_role": "...", "by": "YYYY-MM-DD" }）

## 与 report.json 的关系

将 `root_cause_map` 同步写入 `report.json`，供前端“根因图”页直接展示。

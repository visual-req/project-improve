# 输出（报告/JSON）与前端展示数据

命令指令：`/prjmx:report`

目标：将指标与 ORID 分析汇总成可落盘的报告与结构化 JSON，并确保前端页面可以直接导入展示。

## 输入

- `metrics`
- `orid`
- `root_cause_map`（可选：根因思维导图 JSON）
- `data_integrity`
-（可选）`issues`：从指标异常与样本中抽取的“问题清单（含证据）”
-（可选）`actions`：可执行行动项与排期

## issues（问题清单）生成规则

从以下信号中抽取问题（至少 3 条，最多 8 条）：

- 红/黄指标对应的偏差点
- 趋势恶化且影响范围广的指标
- Top N 异常样本（aging wip、review 延迟、重开等）

每条问题包含：

- `title`
- `severity`（high/medium/low）
- `evidence`（数组：指标事实/样本事实）

## actions（行动项与任务排期）生成规则

每个行动项必须包含：

- `id`（编号）
- `problem`（问题）
- `cause`（原因，建议关联 root_cause_map 的叶子节点）
- `solution`（解决方案）
- `discovered_date`（发现日期）
- `due_date`（按迭代节奏给出）
- `completed_date`（完成日期，可为空）
- `expected_effect`（预期效果，关联指标/趋势）
- `acceptance_method`（验收方法，包含对比窗口/阈值/抽样方式等）
- `owner_role`（负责人角色：PO/SM/Tech Lead/QA/Dev 等）

并按 `due_date` 形成任务排期计划（前端按截止日期排序展示）。

## 行动项建议推理要求（必须）

行动项不是“想到什么做什么”，必须基于 ORID 的过程推理，并充分考虑过程完整性、基线拉升、自动化与复用。

### 1) 过程完整性（先看前置环节是否达标）

在给出行动项前，先回答以下问题（在 solution 与 acceptance_method 中体现）：

- 需求/入口质量是否达标：是否有验收标准、边界条件、依赖、回滚、监控口径；缺失则优先补齐（DoR/检查清单/模板）
- 设计质量是否达标：是否有 ADR/关键决策记录、接口契约/一致性校验、NFR（性能/安全/可用性）约束；缺失则先补齐
- 开发质量是否达标：是否遵循基本规则（命名/复杂度/重复）、是否存在高风险坏味道；缺失则通过规则与自动检查固化
- 评审与 CI 是否达标：评审等待/门禁失败是否是主因；缺失则优先补齐评审 SLA、门禁阈值与自动化检查
- 测试与回归是否达标：是否存在覆盖盲区、关键链路未被保护；缺失则优先补齐自动化测试与回归策略
- 发布与运行是否达标：是否具备灰度/回滚、告警与观测（SLO/阈值）；缺失则优先补齐发布策略与可观测性

### 2) 透明性（把“阻碍点”变成可触发的机制）

行动项中至少包含 1–2 条“透明性/快速反馈”类动作，用于持续发现与验证改进效果，例如：

- WIP/堆积触发：某泳道堆积超过阈值即触发清障（绑定负责人/时限/升级路径）
- 失败聚类触发：CI/发布失败原因聚类后，按 Top N 建立修复/规则固化计划
- 门禁信号触发：扫描/覆盖率/关键用例失败即阻断合并或要求豁免说明

### 3) 基线拉升（把一次性改动变成默认能力）

每个行动项都要回答“如何固化为基线”，优先采用：

- 规范与模板：需求模板/ADR 模板/验收清单/发布清单
- 自动检查：lint/类型检查/扫描/门禁阈值/预提交钩子
- 度量阈值：明确红黄绿与最低可接受变化，并绑定下一窗口对比

### 4) 自动化技术与复用（优先减少重复劳动）

行动项中应覆盖以下主题（按问题相关性取舍，不要求每类都很多）：

- 自动化测试：关键规则/边界/回归用例，优先保护高风险模块与高频返工点
- CI/CD：流水线稳定性、耗时、门禁通过率、发布频率、变更失败率、MTTR
- 复用：沉淀共享组件/脚手架/通用校验库/测试夹具，提升复用度与一致性

### 5) AI 赋能建议（当它能降低成本或减少遗漏时）

若问题与“信息不完整、沟通成本高、重复劳动、失败定位慢”相关，行动项中可以包含 AI 赋能类动作（至少 1 条可选）：

- 结构化：把需求/风险/阻碍/验收/回滚/监控字段化，减少遗漏
- 检查清单：对需求/设计/发布/监控缺口做自动提示与审计抽样
- 归因聚类：对 CI 失败/线上告警/重开条目做聚类，形成 Top N 规则固化
- 生成草稿：PR 摘要、发布说明、测试用例草稿；必须保留人工复核与责任边界

### 6) 行动项质量门槛

- 每条行动项必须可验收：acceptance_method 必须写清楚对比窗口、指标阈值、抽样方式
- 每条行动项必须有“影响路径”：problem → cause → solution → expected_effect（绑定到具体指标）
- 避免“只写培训/宣导”：如果必须培训，则同时给出机制化/自动化落地动作

## report.json（结构化输出）

输出一个对象，字段至少包括：

- `project`（至少包含 id/name/slug_en）
- `data_integrity`
- `metrics`
- `issues`
- `orid`
- `root_cause_map`（可选）
- `actions`

## 落盘路径

按 `work/meta/config.yaml` 的工作区与项目输出目录写入：

- `report.md`
- `report.json`

默认会落到：

- `work/outputs/<project_id>/project-metrics-orid/report.md`
- `work/outputs/<project_id>/project-metrics-orid/report.json`

## 增量与留痕（重复执行）

同一项目重复执行时，不要无条件覆写历史：

- 若存在上一份 `report.json`，先读取并提取上次窗口与关键指标
- 生成本次 `report.json` 时，附带一段 `history.summary`（可选）用于趋势对比
- 保存快照（建议）：
  - `work/outputs/<project_id>/project-metrics-orid/report.<timestamp>.json`
  - `work/outputs/<project_id>/project-metrics-orid/report.<timestamp>.md`

## report.md（Markdown 报告）

必须包含以下章节（顺序建议）：

- 窗口与数据来源概览（项目管理/bug/git）
- 数据完整性诊断
- 指标概览（含红黄绿与趋势结论）
- 问题清单（证据）
- ORID 四段内容
- 行动项与排期计划（表格）
- 下一次复盘检查点与验证方式

## 前端展示验收

确保前端工程（`frontend/`，Vue + Ant Design Vue）能通过导入/粘贴 `report.json` 展示：

- 度量（metrics）
- 问题（issues）
- ORID 过程（orid）
- 根因图（root_cause_map）
- 排期计划（actions）
